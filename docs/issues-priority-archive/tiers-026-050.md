## Tier 26 — Analysis of `docs/weight-tracker-github-issues.md` and `docs/improvement_suggestions.md` (2026-07-20)

_User supplied two external planning documents and asked for a relevance analysis: file GitHub issues for what's genuinely new and worth doing, and for anything that shouldn't be considered now, file it too but mark it Irrelevant/Paused with the reasoning. Both documents predate a lot of what the app has actually built — see the cross-reference note below before picking anything up from this tier._

**Cross-reference note:** significant overlap with already-built features was found and deliberately **not** filed as issues (would be pointless busywork): weekly summaries, the Dashboard itself, CSV/Excel/JSON export, backup/restore, calendar view, cycle tracking, steps-vs-weight and sleep-vs-weight correlation, dark-mode chart theming (#165), and the keyboard-nav audit (#166, already closed clean). The two source documents also directly **contradict each other** on water intake, exercise tracking, and steps/wearable sync — one lists them as things to add, the other explicitly lists them under "things I would remove" — neither side was picked silently. Separately, `improvement_suggestions.md`'s own "Things I would remove" section (protein tracking, mood tracking, meal logging, food database, steps) describes core, already-built, actively-used features — that section appears to predate or misunderstand the app's current state, and no "remove X" issues were filed from it.

## Tier 31 — Found while implementing #233 (2026-07-22)

| # | Status | Issue | Notes |
|---|--------|-------|-------|
| [#262](https://github.com/ZhannaM85/turtle-steps-to-the-goal/issues/262) | ✅ Done | Fixed bottom tab bar reappearing on text-input blur can swallow the very next tap near the bottom of the viewport | Root-caused precisely via a live event trace (Playwright, capturing every pointerdown/mousedown/focusout/focusin/pointerup/mouseup/click with its real target): a first fix attempt (deferring only the `focusout` handler) still failed, because `useIsTextInputFocused.ts`'s `focusin` listener *also* set state directly and synchronously — focusing a non-text control (e.g. the clicked `ToggleGroupItem` button itself) fired `focusin` with that button as `document.activeElement`, synchronously flipping the bar back on *before* the same click's `pointerup` had even been dispatched, so the reappearing bar intercepted `pointerup`/`mouseup`/`click`. Real fix: any transition *out* of a keyboard-opening element — whether reported via `focusout` or via `focusin` landing on a non-keyboard element — now waits for that gesture's own `pointerup` (with a 100ms fallback for a focus change with no pointer involved, e.g. Tab key) before applying; only the transition *into* a keyboard-opening element stays immediate, since hiding the bar can never itself steal a click. Confirmed fixed via the same event trace (pointerup/mouseup/click all land on the real target now) and a new `AppShell.test.tsx` regression test. Closed without a separate device-validation pause — a deterministic logic/timing fix with reproducible before/after proof, not a subjective visual judgment call |
